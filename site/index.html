Overview

What is MLRT?

MLRT (Modern Linux Recovery Tool) is a terminal-based file recovery utility designed for modern Linux filesystems. It demonstrates forensic recovery techniques through deleted inode extraction, journal analysis, and raw data carving. The tool is implemented entirely in Bash and leverages core utilities from The Sleuth Kit (TSK) alongside native Linux tools.

The project is grounded in academic research on filesystem forensics, particularly the 2021 paper "Ext4 and XFS File System Forensic Framework Based on TSK" by Kim et al., which derives metadata changes in Ext4 journal checksum v3 and XFS v5 to build a TSK-based recovery framework.

How It Works

Recovery Pipeline

MLRT executes recovery in sequential phases, each targeting a different layer of data persistence on disk.

Metadata Inode Recovery

Runs fls -rd to enumerate all entries including deleted ones. For each candidate inode, istat verifies the deleted flag, then icat extracts the file content. This recovers files whose inode metadata remains intact but whose directory entries were removed.

Journal-Based Recovery (Checksum V3 Aware)

The Ext4 journal is allocated at inode 8. MLRT parses the journal superblock to verify the magic number 0xC03B3998 and reads the s_feature_incompat flag to determine whether the descriptor format is V2 or V3 (CSUM_V3). The full journal is dumped via debugfs logdump -a, then transaction descriptors and data blocks are analyzed to locate deleted inode backups. When multiple backups of the same inode exist, the most recent is selected by comparing a_time values.

General Text Carving

Extracts all strings of 8+ characters using strings, then for each unique string, grep -aEbo locates its byte offset in the raw image. Data is carved at each offset using dd. This catches any surviving text regardless of filesystem structures.

Pattern-Based Carving

Loads regex patterns from patterns.cfg (format: NAME:pattern), searches the raw image with grep -aEabo, and carves 512-byte blocks at each match offset. Useful for recovering files by signature (e.g., JPEG headers, custom markers).

Research

Academic Foundation

MLRT is based on the research paper "Ext4 and XFS File System Forensic Framework Based on TSK" by Hyungchan Kim, Sungbum Kim, Yeonghun Shin, Wooyeon Jo, Seokjun Lee, and Taeshik Shon (2021), published in Electronics, 10(18), 2310.

Key Findings from the Paper

  • Filesystem evolution impacts forensics — Metadata structures change with version updates (Ext4 journal CSUM_V3, XFS v5), breaking older recovery tools.
  • TSK limitations — The Sleuth Kit lacks native journal-based recovery for Ext4 and does not support XFS, leaving gaps in forensic investigations.
  • Journal analysis is critical — Ext4's ordered-mode journaling backs up inode metadata in journal data blocks, enabling recovery of deleted files even after directory entries are removed.
  • XFS v5 metadata changes — New fields (CRC, UUID) were added for integrity, requiring updated parsing logic for inode extraction.

How MLRT Implements the Research

Ext4 Journal Recovery

The paper describes parsing the journal superblock's s_feature_incompat flag to determine descriptor block format. MLRT implements this by reading the flag at offset 40 in the journal superblock, checking bit 4 (0x10) for CSUM_V3. Deleted inodes are extracted from journal data blocks using debugfs logdump -a and icat.

XFS Metadata Analysis

The paper details XFS v5 metadata structures: superblock, inode core (176 bytes vs 96 in v4), directory entries (shortform/block/node/B+tree), and data extents. MLRT currently uses carving-only for XFS due to limited TSK CLI support, but the research provides the blueprint for full metadata-based extraction.

Comparison with Commercial Tools

The paper compared the proposed framework against TSK, UFS Explorer, and R-Studio across 1 GB and 100 GB datasets:

Usage

Quick Start

Requirements

  • Linux system with Bash
  • Sleuth Kit (fls, istat, icat, debugfs)
  • xfsprogs for XFS, btrfs-progs for Btrfs
  • Standard utilities: dd, losetup, mount, strings, xxd

Create a Test Image and Recover

# Create an ext4 image (keeps mounted for inode recovery)
./vhd.sh create ext4 test.img 512 true

# Copy files to /tmp/mlrt_mount, then delete some

# Run recovery (in another terminal)
./mlrt.sh recover test.img

# List recovered files
./mlrt.sh list

Technical Details

Ext4 Journal Structure

The Ext4 journal is a critical forensic resource. When a file is deleted, its inode metadata may be backed up in the journal area before the deletion is committed. MLRT analyzes three key structures:

Journal Superblock (Inode 8)

Located at the journal's first block. Starts with magic number 0xC03B3998. Contains the s_feature_incompat flag at offset 40 — bit 4 (0x10) indicates CSUM_V3 descriptor format. MLRT reads this via dd + xxd to determine parsing strategy.

Journal Descriptor Block

Contains an array of block tags, each describing a journal data block. The tag structure differs between V2 and V3: V3 adds checksum fields. The t_blocknr field indicates where the data block is stored on disk, linking to the deleted file's inode.

Journal Data Block

Stores the actual backed-up inode metadata of deleted files. MLRT extracts these by matching descriptor block entries with deleted inode numbers, then recovers the inode data using icat.

Why XFS/Btrfs Are Carving-Only

The Sleuth Kit does not natively support XFS or Btrfs for metadata-based recovery. While the research paper describes full metadata analysis for XFS v5 (superblock parsing, inode core extraction at 176 bytes, directory entry traversal, data extent bit-shifting), implementing this requires extending TSK's C codebase. MLRT provides carving as a practical fallback while documenting the metadata approach for future expansion.
